# 配置手册写作规范

配置手册面向客户的系统管理员或接手的实施同事，回答"系统为什么会这样、在哪改、改了影响什么"。目标深度是**看懂 + 敢小改**：读者能改选项值、调审批人、微调自动化，并且改之前知道会牵动什么。不追求"照册从零重搭"，真要复刻用工作区复制，没人照手册手搭，为重搭服务的详尽度只会让文档膨胀。

语言比使用手册可以更"系统"一点（读者是管理员，字段、自动化、审批流这些词可以直接用），但仍然不用开发黑话（trigger、config、API、payload 不写），界面名词用平台原名。

## 一、整体结构

产物形态：成册。章序就是**搭建顺序**，不是功能罗列，标尺是"如果重搭这个工作区，会按什么顺序动手"。

```
# <模块名>配置手册

## 一、成果展示                    ← 固定第一章
## 二、建表与字段                  ← 按依赖序，被依赖的基础资料表在前
## 三、自动化
## 四、审批流
## 五、权限与角色
## 六、页面与工作台
## 七、数据仓库                    ← 有才写
```

**涉及到的层才写**：这个工作区没配审批流，就没有审批流章；章序号顺延。骨架阶段列清每章覆盖哪些表/自动化/流程，让用户确认。

### 成果展示（固定第一章）

让读者翻开第一章就看到"这套配置搭出来是个什么东西"：

- 一张工作区关键截图（工作台或最能代表这套系统的页面）。
- 一段话讲这个工作区支撑的核心业务流和搭建成果。

就这两块，一页以内。不放表清单、不放关系图，细节留给后面各章。

### 每个配置单元的写法

不管哪一层，每个配置单元（一张表、一条自动化、一条审批流）都按同一节奏写：

1. **先说作用**：这个配置是干什么的、解决什么业务问题，一两句话。没说作用不许直接进配置细节。
2. **再讲配置本身**：关键配置项是什么、为什么这么配。写"为什么"优先于写"是什么"：选项值本身界面上看得到，配置意图看不到。
3. **最后讲改动影响**：改这里会牵动什么（见「改动影响」）。

### 章节骨架

```
## 二、建表与字段

本层作用：一两句话（这批表承载什么业务）

### 2.1 <表名>
作用 → 关键字段配置 → 关联关系 → 改动影响
### 2.2 <表名>
…
### 2.x 注意事项        ← 必有
### 2.x 改动影响        ← 必有：本层的跨单元影响汇总
```

## 二、各配置层写什么

### 建表与字段

- 一节一表，按依赖序排。每表讲：这张表承载什么业务、关键字段的配置意图。
- 字段不逐个罗列（界面上看得到），只写**需要解释的**：计算公式（贴公式并讲清业务逻辑）、自动编号规则、显隐条件（什么条件显示、为什么这么设）、关联关系（关联到哪张表、单选还是多选、为什么）、有讲究的默认值和校验。
- 平平无奇的文本、数字字段一句带过或不写。

### 自动化

- 一节一条（或一组同目的的）自动化。讲清四件事：作用、触发条件（什么时候跑）、执行动作（对哪张表做什么）、为什么拆成这样（有设计意图时）。
- 快捷按钮类写清按钮挂在哪张表、点了之后的完整链路。
- 用业务语言描述节点链路（"订单状态变为已审批时，往应收单表新建一条，金额取订单总额"），不贴节点配置 JSON。

### 审批流

- 一节一条流程。讲清：绑定哪张表、什么条件发起、环节顺序和每个环节的审批人规则（岗位/角色，不写姓名）、通过和驳回分别触发什么后续动作。
- 审批人规则写配置逻辑（"取发起人所在部门的负责人"），这正是管理员最常要改的地方。

### 权限与角色

- 按角色组讲：这个角色是给谁用的、能看哪些表、关键的字段级/记录级权限设置和设置原因（"销售只能看自己的客户，靠「负责人=当前成员」的记录权限实现"）。
- 不逐表逐字段列权限矩阵，只写有业务含义的权限设计。

### 页面与工作台

- 每个页面讲：给谁看的、放了哪些组件、数据来自哪张表哪个视图、筛选条件的口径。
- 统计图表写清统计口径（"只统计本月已审批订单"），这是最容易被问"这个数怎么来的"的地方。

### 数据仓库（有才写）

- 每张聚合表/同步表讲：为什么要建（普通表算不动什么）、源表和汇总口径、更新周期。

## 三、改动影响

这是配置手册区别于一份配置导出的核心价值，管理员真正的痛点是"想改不敢改"。

- 每个配置单元的"改动影响"写清：这个字段/自动化/流程被谁引用（哪些公式、自动化、页面组件依赖它），改名/改选项/删除分别会断什么。
- 依据来自 hac 引用查询或实测，**不编**。查不到又拿不准的标 `[待确认]`。
- 高危改动（删字段、删自动化、改关联关系）用「⚠️」加强警示，并给出安全做法（先停用观察、先在测试表验证、改前导出备份）。
- 常规安全改动也要明说（"改选项文字不影响已有数据和自动化，放心改"），敢改和不敢改的边界都给清楚。

## 四、配图

密度低于使用手册：不追求每步一图，每类配置给两类图。

- **入口图**：这个配置在哪改（表设置入口、自动化列表、审批流列表），标注框标出入口位置。
- **编辑界面图**：打开后的配置界面长什么样（字段设置面板、自动化编辑器、审批流设计器），让读者确认"我打开的就是这个"。
- 同构的配置（十条自动化的编辑器长得一样）只截一张代表图，正文说明其余同理。
- 标注框与脱敏标准见 [walkthrough-guide.md](walkthrough-guide.md) 第四、五节；框的含义写在正文步骤文字里。
- 走查时**只读不改**：可以打开编辑面板截图，不保存、不提交、不改动任何已有配置。

## 五、注意事项与标记

- 每章"注意事项"写实测到的系统硬边界（配置项之间的互斥、平台限制、版本差异）。
- 常见问题章不强制；有管理员高频问题（"怎么加一个审批环节""怎么给新员工开权限"）时按使用手册的常见问题写法写。
- `[待确认]` / `[待补充]` 标记同使用手册。
