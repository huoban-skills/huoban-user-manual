# 使用手册写作规范

使用手册面向业务操作者，只回答"我该做什么、系统会给我什么"。配置的内部原理（自动化的触发条件和执行节点、审批流怎么设计、字段显隐的配置逻辑）不写，那是配置手册的内容；配置产生的**表面行为**照写（"总金额系统自动算，不用手填""提交后进入采购审批""单号自动生成"）。计算字段的公式保留在使用手册（见「字段写法」，业务流程章揉步骤、基础资料章用表格）。

## 一、整体结构

### 整册骨架

```
# 模块名                      ← 不追加"使用手册"

模块介绍：整册的场景通识，写法见「场景介绍写法」

（业务流程模块）整册一张全流程图，见「业务流程图」

目录（HTML 预览自动生成，md 里不手写）

## 一、章节名

场景介绍：本章业务动作的场景通识，写法见「场景介绍写法」

### 1.1 <通识名>              ← 可选：必须先懂的机制各占一节，标题就是机制名
                                 （如「产品/物料的唯一性」），放操作小节前，讲机制不讲操作
### 1.x 操作名                ← 三级标题必须编号；多个操作依次排
### 1.x 常见问题              ← 必有，不许只在文末放全局的
### 1.x 注意事项              ← 必有，写法见「注意事项写法」
```

- **正文一律标准 Markdown**：标题用 `##` / `###`，步骤用 `1. 2. 3.`，要点用 `-`；不用 `<h4>` `<ol>` `<li>` 这类 HTML 标签写正文（md 编辑器会整块显示成灰底 HTML，图也挂不进步骤条目）。唯一的例外是图注行的 `<small>`。
- 一个章节只讲一件事，藏着两件事就拆两章。全册级的主线和通识只住在册头模块介绍里，不单开"使用前先看""阅读说明"类章节。
- 模块带工作台/首页页面的，工作台固定作第一章：它是读者每天进系统的第一站，讲快捷入口、指标口径（数字从哪来、什么范围）、待办清单和跟踪页签；查询和口径类说明写在这里，后面各章不再重复。
- 模块类型二选一，决定章节单位。不要把业务流程模块写成单表手册：
  - **基础资料/数据维护**：一章一表，规则见「基础资料模块」。
  - **业务流程**：一章一个业务闭环，如销售报价、订单、发货、收款。

### 基础资料模块

- 一章一表，按依赖排序，被依赖的在前；分类、类目这类被引用的小表排最前。期初类表演示环境有就按依赖序排进清单，没有不写。
- 固定含**「基础资料导入说明」章**，放最前（有工作台章则排其后），三块内容：
  - **导入创建**：切换「导入模板」视图 → 选若干数据导出 Excel 即模板 → 照格式填写（数据唯一编号不填）→ 导入。
  - **导入修改**：筛选导出要改的数据（含要改的字段）→ 只改内容、不动数据唯一编号 → 导入时选"仅更新数据"、依据字段为数据唯一编号、不更新的字段不导。
  - **导入常见问题**：失败看右上角通知下载失败文件（末列有原因）；表里没数据先手工造一条才能导出模板；模板字段不全先加字段、再调「导入模板」视图的显示列。
- 各资料表章只写自己的导入特殊点（有才写），通用流程引用导入说明章，不重复。
- 资料表的不同用法各开一个操作小节：基本新增一节，有讲究的特性场景（多单位、批次、规格属性）各一节，演示环境实际启用了才写。
- 册头按维护顺序叙事，字段说明用三列表格（见「场景介绍写法」「字段写法」）。

### 场景介绍写法

册头的模块介绍和章开篇的场景介绍是同一种写法，只差范围：册头讲整个模块的业务，章开篇讲本章这一个业务动作。都是给读者补场景通识，不是产品说明。

- **第一句先说"是什么"**：册头和章开篇都先用一句话定义（"商品资料是所有单据选产品时取数的档案"），再接场景。
- **业务流程模块的册头按时间线叙事**：像给新同事介绍一单生意怎么走完，一条主线贯到底，末尾带一句读者收益。
- **基础资料模块的册头按维护顺序叙事**：先建什么、再建什么、建好后被哪些业务引用（"先建商品分类，再建商品资料，最后维护仓库；后面下单、出入库都从这里取数"）。
- **章开篇讲使用时机**：从读者熟悉的业务情境写起，讲清什么情况下用到、帮读者把什么事办成。
- 用之前必须知道的通识也写在这里：这张单影不影响库存、状态什么时候变、和上下游哪张单衔接。
- 前置条件也在这里一句话说清（要先建好什么资料、需要什么权限、来源单据要是什么状态），不单开小节："到货状态变成「已到货」、实物到仓后，按下面步骤办理入库"。
- 有几个典型情境就分场景列（"场景一：客户下单前先询价…"），最多三个，都来自真实业务，不为覆盖功能编。

### 章节归属

- 主单据和明细表构成同一业务动作时不拆两章；明细表有独立业务含义才单独成章。
- 入口不决定归属：按钮在订单表上，不代表内容写进订单章；本身是独立业务闭环（如销售退货）就单独成章，步骤里说明从哪发起。
- 主-明细表族（如工艺+工艺路线）在同一大章下用子标题组织，介绍讲清表间关系（"工艺是目录，工艺路线是正文"）。
- 每个场景只写在它所属的模块手册里（建档归基础资料，对账核销归应收/应付）；不属于本模块的操作用引导语带过，且必须补半句业务缘由：
  - ✅ "采购入库确认后，对账付款要到「应付管理」继续，只有在那里核销这笔采购才算财务结清，详见对应手册。"
  - ❌ "供应商对账、付款录入属于「应付管理」模块，详见对应手册。"

### 业务流程图（一册一张）

整册只配一张全流程图，放在册头模块介绍后面，用 `scripts/flow.py` 从 flow.json 渲染成 SVG，不手画。各章开篇不再配流程图，**不单开"业务流程"小节**，三级标题只放操作名。

- 图覆盖整个模块的业务主线：分组是业务阶段或岗位环节（"销售环节""财务环节"），组内步骤按顺序竖排。
- 每个步骤标落在哪张表（副行），表名与本册章节对应，读者看图即知去哪章找操作细节。
- 系统自动完成的环节标 `"auto": true`（置灰虚线），读者一眼看清整个流程自己要动手几次。
- 它在第一章之前，图注不编图号，直接写一句业务话（"从报价到出库的全流程"），文件存 `images/0-全流程总览.svg`。
- 基础资料模块没有业务主线，不配流程图。

### 步骤写法

- 格式：先用一句话说场景，再接编号步骤。只有一个场景时场景句加粗即可，不加"操作场景"标题。
- 步骤动词开头；关键步骤后跟一句系统的预期反馈（"保存后列表里出现这张订单，状态为草稿"）；结果融入最后一步。
- 禁止"触发时机/操作步骤/操作结果"三段式。

### 字段写法

按模块类型分两种：

**业务流程章：字段揉进步骤**，不单开小节、不做字段表。

- 必填在步骤里点出（"填写客户、入库仓库和入库数量，这三项必填"）。
- 值得多说一句的才说：默认值从哪来（"新建时默认今天""从订单发起时自动带「退货入库」，无需修改"）、显示条件（"出库类型选「销售出库」后才显示"，不写显隐怎么配置的）、自动计算（先用业务语言讲逻辑，再附公式原文，读者核数时用得上）、关联带出（"从XX表自动带入，仅供查看"）、填错有后果的。
- 界面一看就懂的字段（名称、备注、电话）一个字不提；状态字段的流转在步骤反馈和场景介绍里顺着业务讲；流程状态、流程发起人等平台过程字段不写。

**基础资料章：字段用表格**，跟在新增小节的步骤后面。录入档案是逐字段照着填，表格好查。

- 格式 `| 字段 | 字段说明 | 填写说明 |`，按表单顺序列全字段，表单有分组时按分组分段。
- 字段说明讲业务含义：这个字段是干什么的、编号怎么构成、被哪些业务引用（"库存核算的最小单位；已有出入库记录后严禁修改，否则库存数量混乱"）。
- 填写说明写 `必填` / `选填` / `自动计算，无需填写`；条件必填写清条件（"来源为自制时必填，否则无法自动生成工序任务"）。

### 审批流程

- 作为业务动作的一个环节写进对应章节（"提交后进入采购审批"），不单开大章、不画流程图。
- 写清三件事：什么时候触发、谁来审（环节名，写岗位不写姓名）、通过和驳回后系统分别会怎样（"审批通过后采购状态自动变为待入库"）。审批流内部怎么设计的不写。
- 未启用的流程不写；环节没采集到标 `[待确认]`，不编。


### 注意事项写法

- 不止提醒，要写实测到的**系统硬边界**：什么情况下按钮置灰或操作不允许、改这里会联动改哪里、删除后能不能恢复。来源是实测或配置，不编。
- 操作性提醒（易填错、易点错的）照写。

### 外部平台的出处

跨平台内容里，凡是**来自外部平台的东西都要给出处**，两类都算：

- 要填的值（ID、密钥、回调地址）：给获取页面链接 + 获取步骤的分步截图，不许只写"填入XX即可"。
- 要照抄的规格（请求体格式、参数、频率上限）：给对方官方文档链接并说清是谁定的规矩。链接要实际打开核过，不能凭印象写。
- 特别注意从演示环境里读出来的配置：它是实测所得，但**规格的出处仍然在外部平台**，照抄进文档一样要给官方链接。

## 二、语言与例子

- **读者是一线使用者本人**，像跟同事解释，不要说明书腔调；也别写「跟客户解释时可以说」这类把读者当顾问或实施方的句子。
- 「客户」只在指**读者自己的业务对象**时才用（报价单发给客户、客户要 Excel 版），不要用来指读者服务的对象。
- 禁止技术术语（validator、trigger、automation、config、API 等）："数据触发自动xxx"→"系统会自动xxx"；"validator 校验"→"保存时系统会自动检查，xxx时弹窗提示"。
- **不说"记录"，说具体的表单数据**：✅"保存后生成一条入库单" ❌"保存后生成一条记录"。读者认识的是单据和资料，不是"记录"。
- 界面名词用平台/系统原名，不转述不生造。
- 损耗率、转化率这类不直观的概念，用 `>` 引用块配具体例子。例子贴读者行业，给到能照着填的具体值（"1 包=3 个，1 箱=15 个"），不停留在"如某商品"；拿不准标 `[待确认]`。
- **本规范里的例句只示意结构**：措辞不得照抄，更不得跨章复用成模板（机检会抓重复句）。
- **表述层全按 [user-manual-humanize.md](user-manual-humanize.md) 执行**：复读与模板、陈词、套路句式、安抚词密度、加粗滥用、收尾，那里是唯一事实源。

## 三、常见问题写法

- 每个问题写成**加粗编号行**：`**1. 为什么我这单提交不了？**`，编号小节内从 1 连续；不用 #### 标题，那在普通编辑器里字号太大。
- 问题用业务人员真实会问的大白话提问：✅"为什么我这单提交不了？" ❌"提交校验规则说明"。手册后期会被 AI 内化按口语提问召回，问题越像真人问的越准。
- 回答按「原因 → 解决办法」组织，多个原因逐条给解法，结尾说一句解决后是什么样。

## 四、配图

图是给读者定位用的，每张图都要回答"我现在该看屏幕哪里"。

- **图注写两处、文字一致**：alt 位置一处，图片下方单独一行再写一遍。alt 只有 HTML 才显示，md 编辑器里看不到，下方那行是给 md 读者的：

  ```
  ![图 2-3：点右上角「新建」按钮](images/2-3-新建入口.png)

  <small style="color:#8A8F98">图 2-3：点右上角「新建」按钮</small>
  ```

  下方那行用 `<small style="color:#8A8F98">` 包起来，md 编辑器里就是灰色小字，跟 HTML 预览的观感一致（个别渲染器会忽略颜色，退化成小字，不影响阅读）。

  格式 `图 <章节号>-<序号>：<读者视角一句话>`（"点右上角「新建」按钮"，不写"截取了新建按钮"）。图片一律相对路径，与文档同级放 images 目录；正文说「如图 2-3」时被引用的图必须存在。
- 配几张图、标注框何时画、多框序号、脱敏选区，标准都归 [walkthrough-guide.md](walkthrough-guide.md)，那里是唯一事实源。写作侧只承担一条：**每个框的含义落在步骤文字里**。多框按 ①②③ 顺序写清每个序号是什么（"①处点开筛选，②处选择日期范围"），单框对应的动作也必须出现在所在步骤的文字中，含义不写进图内。
- 图挂在**图注所描述的那一步**下面（列表项内缩进 4 空格），判定就看图注：图注写"核对发货明细"，图就紧跟在讲核对明细的那一步后面，中间不隔别的步骤、段落或代码块，更不许把几张图都堆在序列末尾。做到一段文字一张图交错往下走。
- **菜单路径默认不挂链接**，只有读者会卡住的地方才挂直达链接：
  - **菜单名和文档里的叫法对不上**（控制台左栏叫「服务及函数」，文档写「函数列表」）。给链接，并补一句实际的菜单名。
  - 相邻两张图之间隔着好几次点击，中间没有连续截图。
  - 外部平台的控制台：地域、账号、版本不同菜单会变，链接比截图稳。
