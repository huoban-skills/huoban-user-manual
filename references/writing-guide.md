# 使用手册写作规范

使用手册面向业务操作者，只回答"我该做什么、系统会给我什么"。配置的内部原理（自动化的触发条件和执行节点、审批流怎么设计、字段显隐的配置逻辑）不写，那是配置手册的内容；配置产生的**表面行为**照写（"总金额系统自动算，不用手填""提交后进入采购审批""单号自动生成"）。计算字段的公式保留在使用手册（见「字段表」）。

## 一、整体结构

产物形态唯一：**成册模块手册**。结构单元只有章节，一个章节讲一个业务动作或场景；单场景就是只有一章的册子，同样套册头。

### 整册骨架

```
# 模块名                      ← 不追加"使用手册"

模块介绍：管什么业务、谁在用、业务主线，三五句

目录（HTML 预览自动生成，md 里不手写）

## 一、章节名

场景介绍：是什么、为什么、怎么做的简要概括（不加"业务定位"标题）

（业务流程章）开篇业务流程图，见「业务流程图」

### 1.1 操作名                ← 三级标题必须编号；多个操作依次排
### 1.x 字段说明              ← 唯一的可选件，写不写在定骨架时让用户定
### 1.x 注意事项              ← 必有，只放系统级事项（见「注意事项写法」）
### 1.x 常见问题              ← 必有，不许只在文末放全局的
```

**模块介绍**（册头那段）写三件事，控制在三五句，不写成摘要也不吹功能：

- **管什么业务**：这套东西覆盖哪些事，边界在哪（"覆盖库存查询、出入库办理和盘点；采购下单、销售报价不在本册"）。
- **谁在用**：读者是哪个岗位，一句话点明（"给一线库管使用"）。
- **业务主线**：这套东西按什么顺序用，文本箭头串一条（"来源单据审批通过 → 库管核对仓库批次数量 → 完成出入库 → 回查库存"）。

模块级的口径（金额正负数代表什么、状态怎么划分、以谁为准）也放这里先讲清，别散落到各章。

**章内规则**：

- **字段说明表是唯一要问用户的可选件**。审批说明固定写：不占独立小节，作为业务动作的环节写进步骤（见「审批流程」）。
- 一个章节只讲一件事，藏着两件事就拆两章。
- 前置条件（要先建好什么资料、需要什么权限、来源单据要是什么状态）不单开小节，揉进章开篇的场景介绍里一句话说清："到货状态变成「已到货」、实物到仓后，按下面步骤办理入库"。

### 成册编排

- 册末固定含「典型业务场景」章，写法见下文。
- 模块类型二选一，决定章节单位。不要把业务流程模块写成单表手册：
  - **基础资料/数据维护**：一章一表，按依赖排序，被依赖的在前。
  - **业务流程**：一章一个业务闭环，如销售报价、订单、发货、收款。

### 章节归属

- 主单据和明细表构成同一业务动作时不拆两章；明细表有独立业务含义才单独成章。
- 入口不决定归属：按钮在订单表上，不代表内容写进订单章；本身是独立业务闭环（如销售退货）就单独成章，步骤里说明从哪发起。
- 主-明细表族（如工艺+工艺路线）在同一大章下用子标题组织，介绍讲清表间关系（"工艺是目录，工艺路线是正文"）。
- 每个场景只写在它所属的模块手册里（建档归基础资料，对账核销归应收/应付）；不属于本模块的操作用引导语带过，且必须补半句业务缘由：
  - ✅ "采购入库确认后，对账付款要到「应付管理」继续，只有在那里核销这笔采购才算财务结清，详见对应手册。"
  - ❌ "供应商对账、付款录入属于「应付管理」模块，详见对应手册。"

### 业务流程图（业务流程章开篇）

业务流程章的场景介绍后面配一张流程图，用 `scripts/flow.py` 从 flow.json 渲染成 SVG，不手画：

- 分组是业务阶段或岗位环节（"销售环节""财务环节"），组内步骤按顺序竖排。
- 每个步骤标落在哪张表（副行），表名与本册章节对应，读者看图即知去哪章找操作细节。
- 系统自动完成的环节标 `"auto": true`（置灰虚线），读者一眼看清整个流程自己要动手几次。
- 基础资料章不配流程图。

### 步骤写法

- 格式：先用一句话说场景，再接编号步骤。只有一个场景时场景句加粗即可，不加"操作场景"标题。
- 步骤动词开头；关键步骤后跟一句系统的预期反馈（"保存后列表里出现这条记录，状态为草稿"）；结果融入最后一步。
- **区分必要与非必要**：系统已兜底的动作不写成必做步骤。系统有数据唯一性校验就不写"先人工搜索确认不重复"；确实建议做但非必须的，明说"可以…，不做也不影响，系统会…"。
- **重要步骤的注意事项写在步骤里**：容易做错、做错代价大的步骤，警示紧跟这一步写，不攒到文末。会严重影响数据安全的操作（批量删除、覆盖导入、修改已核销单据），在步骤处用「⚠️」加强警示并给出正确做法。
- 禁止"触发时机/操作步骤/操作结果"三段式。

### 字段表

格式 `| 字段 | 填写方式 | 是否必填 | 说明 |`，不拆"手动/自动"两组表，填写方式列区分 `手动填写` / `系统自动`。

- 顺序对齐表单主区布局（form-layout 的 main_layout），和操作者看到的表单一致。
- 说明列写法：
  - 显示条件字段：写清出现条件（"出库类型选「销售出库」后才显示"），不写显隐是怎么配置的。
  - 计算字段：先用业务语言讲逻辑（"订单总金额减已收款金额，系统自动算，不用手填"），再附公式原文，读者核数时用得上。
  - 自动编号：写清单号构成（"DD + 年月日 + 3位流水，每天从001重计"）。
  - 默认值：标注（"新建时默认今天""从订单发起时自动填「退货入库」，无需修改"）。
  - 关联字段标 `→ 目标表名`；关联附加字段填写方式写 `系统自动`，说明"从XX表自动带入，仅供查看"。
- 流程状态、流程发起人等平台过程字段不写；订单状态、待收款总额等业务判断字段要写。

### 审批流程

- 作为业务动作的一个环节写进对应章节（"提交后进入采购审批"），不单开大章、不画流程图。
- 写清三件事：什么时候触发、谁来审（环节名，写岗位不写姓名）、通过和驳回后系统分别会怎样（"审批通过后采购状态自动变为待入库"）。审批流内部怎么设计的不写。
- 未启用的流程不写；环节没采集到标 `[待确认]`，不编。

### 典型业务场景（册末固定章）

单章教会读者一个动作，这一章教会读者把几个动作串成一件事，专治"每张表都会用、业务串不起来"。

- 每个场景用一线员工的真实问法开头："跟供应商约定每月 5 号付未结货款，怎么处理？"，不用归纳式标题。
- 步骤跨章串联：只写串联点（在哪张表做什么、状态怎么流转到下一步），单步细节引用对应章节，不重复。
- 场景来自用户提供或实测观察到的真实业务，不为覆盖功能强行编。

### 注意事项写法

- 章末"注意事项"只放**系统级**事项：什么情况下按钮置灰或操作不允许、改这里会联动改哪里、删除后能不能恢复。来源是实测或配置，不编。单个步骤的操作性提醒写在步骤里，不重复放到章末。
- **分警示等级**：普通提醒平铺直叙；会严重影响数据安全和管理的（不可恢复的删除、会连带改动其他表数据的操作）条目以「⚠️」开头加强警示，并紧跟正确的操作方式。

### 基础资料的数据整理

基础资料章涉及存量数据导入时，不自制数据整理模板：写清在系统里下载导入模板的入口和步骤（表格 → 导入 → 下载模板），引导读者用系统模板整理数据，避免自制模板与系统真实导入格式不一致。

### 外部平台的出处

跨平台内容里，凡是**来自外部平台的东西都要给出处**，两类都算：

- 要填的值（ID、密钥、回调地址）：给获取页面链接 + 获取步骤的分步截图，不许只写"填入XX即可"。
- 要照抄的规格（请求体格式、参数、频率上限）：给对方官方文档链接并说清是谁定的规矩。链接要实际打开核过，不能凭印象写。
- 特别注意从演示环境里读出来的配置：它是实测所得，但**规格的出处仍然在外部平台**，照抄进文档一样要给官方链接。

## 二、语言与例子

- 面向一线操作人员，像跟同事解释，不要说明书腔调。
- **手册是给用这套东西的人看的，不是给服务他的人看的。** 别写「答客户『能不能做成 XX 样』时照这个表回答」「跟客户解释时可以说」这类句子，它把读者预设成了顾问或实施方，而读者往往就是使用者本人。改成直接对读者说：「想知道能还原到什么程度，对着这个表看」。
- 「客户」只在指**读者自己的业务对象**时才用（报价单发给客户、客户要 Excel 版），不要用来指读者服务的对象。
- 禁止技术术语（validator、trigger、automation、config、API 等）："数据触发自动xxx"→"系统会自动xxx"；"validator 校验"→"保存时系统会自动检查，xxx时弹窗提示"。
- **不说"记录"，说具体的表单数据**：✅"保存后生成一条入库单" ❌"保存后生成一条记录"。读者认识的是单据和资料，不是"记录"。
- **少用简写，用大白话**：不把"盘点时间点"缩成"盘点时点"；行话先解释再用；一个词读者可能要停下来想的，就换更直白的说法。
- 界面名词用平台/系统原名，不转述不生造。
- 损耗率、转化率这类不直观的概念，用 `>` 引用块配具体例子。例子贴读者行业，给到能照着填的具体值（"1 包=3 个，1 箱=15 个"），不停留在"如某商品"；拿不准标 `[待确认]`。
- **不吹功能**：删掉"强大""高效""极大提升"这类形容词，价值用具体业务结果说（✅"少录一遍数据" ❌"大幅提升录入效率"）。
- **收尾即停**：写完最后一步就结束，不加"配置完成后，您的团队协作将更加顺畅"式展望，也不写"希望本文对你有帮助"。
- **句式不套路**：不硬凑"不仅…还…""从…到…"和三个一组的排比；破折号不用，断句或用冒号。
- **废话压缩**："具有导出能力"→"能导出"；不叠限定词（"可能在部分情况下或许"），拿不准就实测，实测不了标 `[待确认]`。

## 三、常见问题写法

- 小标题用业务人员真实会问的大白话提问：✅"为什么我这单提交不了？" ❌"提交校验规则说明"。手册后期会被 AI 内化按口语提问召回，问题越像真人问的越准。
- 回答按「原因 → 解决办法」组织，多个原因逐条给解法，结尾说一句解决后是什么样。

## 四、配图

图是给读者定位用的，每张图都要回答"我现在该看屏幕哪里"。

- 每个操作序列至少三类图：**入口图**（在哪点，标注框标出）、**过程图**（表单/弹窗）、**结果图**（系统反馈）。能合并的合并，不为凑数一步一图。
- 图注写在 Markdown 图片的 alt 位置：`![图 <章节号>-<序号>：<读者视角一句话>](images/xxx.png)`（"点右上角「新建」按钮"，不写"截取了新建按钮"）；正文提到某张图时说「如图 2-3」，被引用的图必须存在。
- 图片一律相对路径（`images/…`），与文档同级放 images 目录，任何 Markdown 编辑器打开都要能看到图。
- 标注框何时画、多框序号、选区合并和脱敏的标准都归 [walkthrough-guide.md](walkthrough-guide.md) 第四、五节，那里是唯一事实源。写作侧只承担一条：**每个框的含义落在步骤文字里**——多框按 ①②③ 顺序写清每个序号是什么（"①处点开筛选，②处选择日期范围"），单框对应的动作也必须出现在所在步骤的文字中，含义不写进图内。
- 图放进它对应的步骤条目里，做到一段文字一张图交错往下走。
- 弹窗、抽屉用局部截图；整页图只用于交代位置。
- **入口不好找、或者两张图之间有跳跃时，把直达链接挂上。** 图只能证明「长这样」，证明不了「从哪进去」。下面几种情况光靠图读者会卡住：
  - **菜单名和文档里的叫法对不上**（控制台左栏叫「服务及函数」，文档写「函数列表」）。给链接，并补一句实际的菜单名。
  - 入口藏在多级菜单里，或者要先点开别的东西才出现（比如面板要点卡片上的齿轮才弹出来）。
  - 相邻两张图之间隔着好几次点击，中间没有连续截图。
  - 外部平台的控制台：地域、账号、版本不同菜单会变，链接比截图稳。
  - **导航里没有这个功能入口时**，不能只写"打开XX表"：给直达链接，或写清从「表格」入口找到该表的路径。
- 字段的界面表现（显隐、默认值）写进字段表说明列，字段表里不放图。

## 五、标记

- `[待确认]`：需要用户校正（不确定的业务逻辑、推测的字段含义、拿不准的例子）。
- `[待补充]`：需要后续积累（暂无内容的常见问题、注意事项）。
